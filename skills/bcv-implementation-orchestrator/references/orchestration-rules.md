# Orchestration rules

## Purpose

Define how `bcv-implementation-orchestrator` coordinates the implementation of an
approved `technical-story-enriched.md` across multiple BCV specialized skills.

## Core rules

1. **No code generation**
   - This skill only produces prompts and orchestration plans.
   - Source code is generated by the specialized skills listed in
     `implementation-task-to-skill-mapping.md`.

2. **Respect task status — strict blocking**
   - `TODO` tasks get a generated prompt and are queued for execution.
   - `BLOCKED` tasks are **never** executed and **never** get a generated prompt.
   - For `BLOCKED` tasks, only record: blocked-by, unblock condition, impact if not unblocked and assigned skill.
   - If a task depends on a `BLOCKED` task, it is also treated as blocked.
   - Do not create files under `implementation-prompts/` for `BLOCKED` tasks.

3. **Respect dependencies**
   - Build a dependency graph from `Dependencies` and `Unblock condition`.
   - Order tasks topologically.
   - Never suggest executing a task before its dependencies are done.

4. **No requirement invention**
   - Every prompt must derive from the story and impact analysis.
   - Do not add features, validations or flows not present in the story.

5. **Use only available skills**
   - If the user provided `available_skills`, assign only skills from that list.
   - If the default mapped skill is not in `available_skills`, mark the task as `MANUAL`.
   - If no `available_skills` is provided, output skill categories and let the user map them.
   - Never invent a concrete skill name that the user has not confirmed.

6. **Preserve traceability**
   - Each prompt must reference the HU criterion, IMP-XXX task and impact item.
   - The orchestration plan must reference both source files.

7. **One prompt per executable task**
   - Each `TODO` task becomes a self-contained prompt file.
   - A developer can copy-paste the prompt into the target specialized skill.

8. **Group by service when useful**
   - If multiple tasks affect the same service, group them under a service heading
     in the orchestration plan for clarity.

9. **Respect stack**
   - Read `analysis_scope.stack` from the impact analysis.
   - If the stack is not Java/Spring Boot, do not force Java-specific skills.
   - When the stack has no matching specialized skill, mark backend tasks as `MANUAL`.

## Output rules

- Read `technical-implementation-blueprint.yaml` as the primary input when available.
- Write the orchestration plan to `docs/historial/<hu-slug>-implementation-orchestration-plan.md`.
- Write one prompt per executable `TODO` task to `docs/historial/<hu-slug>-implementation-prompts/`.
- Do not create prompt files for `BLOCKED` or `MANUAL` tasks.
- Do not infer services, repositories, files or skill mappings when the blueprint provides them.

## Review and sign-off

The orchestration plan should include a developer review section so a human can
validate that:

- The right specialized skill was chosen for each task.
- The order of execution is correct.
- No task is missing or incorrectly blocked.
- The prompts are self-contained and actionable.
